# Profiles 与结构槽位

## 初始化深度

### `skeleton-only`

建立或确认一个产品 Git 仓库。除 `.git` 外不创建入口、文档、空目录、占位文件、commit 或 remote。

该深度不提供自动读取链，适用于仅需先确立仓库边界的场景。

### `mapped`

建立最小可用读取链：

```text
<REPOSITORY_ROOT>/
├── <NATIVE_ENTRY>...
└── <DOCS_ROOT>/
    ├── <DOCUMENT_INDEX>
    └── <REAL_FACT_DOCUMENT>...
```

每种已确认的原生入口格式一个文件，全部直接链接同一个文档索引。索引链接真实存在的事实文档。没有事实内容时不要创建空模块；在索引中明确目前可用的权威来源即可。

### `structured`

在 `mapped` 上选择有维护者和用途的模块，例如：

- 产品规格与验收标准。
- 架构、接口或领域词汇。
- 决策记录。
- active/completed 计划。
- 质量门、验证证据或运行手册。
- 多 Agent 角色、文件所有权、评审和 worktree 协议。
- 文档新鲜度、依赖边界或目录规则的 linter/test/CI。

不要自动创建 `src/`、`tests/`、应用框架、依赖或 CI。它们必须来自用户目标或项目已有技术栈。

## Agent 数量不改变仓库拓扑

单 Agent、双 Agent或更多角色都使用同一个权威仓库。角色数量只会影响：

- 哪些原生入口类型确实需要存在。
- 是否需要正式协作文档。
- 读取、写入、评审和合并职责。
- 是否需要按任务建立独立 worktree。

不要按 Agent 创建重复的事实树。工具或角色真正私有的短期状态留在宿主原生存储，或进入明确 ignored 的本地目录。

## 原生入口能力矩阵

对每种目标工具记录：

| 字段 | 含义 |
|---|---|
| Tool/Agent ID | 用户可识别的名称 |
| Native entry path | 从仓库根启动时实际读取的相对路径 |
| Evidence | 用户指定、现有配置或当前官方文档 |
| Can share entry | 是否与其他角色共用同一文件 |
| Required syntax | 例如普通 Markdown 或特定 rule 格式 |
| Fallback | 无原生入口时的手动启动说明 |

文件名只是配置。不要仅因常见示例就断言某工具读取 `AGENTS.md`、`CLAUDE.md` 或 `.cursor/rules`；工具行为可能随版本和设置变化。

## 薄入口内容槽位

一个入口通常只需要：

1. 仓库根和 Git 边界。
2. 文档索引的真实相对链接。
3. 最小必读顺序和按需读取规则。
4. 极少量必须在读取文档前生效的安全、权限或写入边界。
5. 链接缺失、事实冲突或状态不明时的失败行为。

多个工具入口的这些内容可以少量重复。不要创建入口之间的跳转链；让每个入口直接到共同文档索引，避免循环和某个工具缺席时断链。

## 文档索引槽位

索引为每项链接说明“它回答什么问题”或“什么时候读”，使 Agent 能按任务只加载相关文档。优先扁平、可扫读的地图；文档多到无法直接导航时再增加子索引。

事实文档应声明适用范围、状态或最近验证信息，只在这些信息能被维护时加入。当前计划应有明确完成条件；已完成计划可以归档，但移动或归档已有文件属于演进操作。

## 忽略目录槽位

若选择本地私有或临时目录：

- 名称必须与现有项目不冲突。
- `.gitignore` 使用足够窄的规则，不用覆盖宽泛用户路径的 glob。
- 只在有实际文件时创建目录；Git 不跟踪空目录。
- 验证时对目录下的探针路径运行 `git check-ignore --no-index`，即使目录尚不存在也能确认规则。

## 推荐起点

| 场景 | 推荐 |
|---|---|
| 只确立新的 Git 边界 | `skeleton-only` |
| 让一个或多个工具可靠找到项目事实 | `mapped` |
| 长期项目、事实类型较多或需要机械护栏 | `structured`，只选真实模块 |
| 旧入口过长、事实重复 | `evolve` + `mapped/structured` |
| 从产品仓库 + Context 仓库迁移 | `evolve` + `structured`，先读迁移规则 |
